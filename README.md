# Call Me Maybe

Translate natural language prompts into structured JSON function calls using constrained decoding with a local LLM (Qwen3-0.6B).

---

## Description

Given a set of function definitions and a natural language prompt, this tool selects the correct function and extracts its arguments — without fine-tuning or prompt-engineering the model to output valid JSON. Instead, it uses **constrained decoding**: at each generation step, invalid tokens are masked to `-∞` before argmax, so the model can only produce output that conforms to the expected structure.

## Algorithm

### Function selection — constrained decoding

The model selects a function name token by token. At each step:

1. Compute the full vocabulary logits from the current context.
2. Build a mask: set all positions to `-∞`, then restore only token IDs whose string keeps the generated prefix as a valid start of at least one function name.
3. Take `argmax` of the masked logits — the model cannot emit an invalid token.
4. Append the chosen token and repeat until the closing `"` is generated.

This guarantees a valid function name in every case, regardless of what the model would otherwise prefer.

### Argument extraction

- **Numeric parameters**: extracted directly from the prompt using the regex `r'-?\d+(?:\.\d+)?'`. Numbers appear literally in the prompt, so LLM generation is unnecessary and would introduce noise.
- **String parameters**: generated by the model using greedy decoding (unconstrained `argmax`), stopping as soon as the model emits a token containing `"`. The prompt format is chosen per parameter type:
  - `regex`/`pattern`: code-completion format (`# <prompt>\nregex = "`) steers the model toward valid regex syntax, leveraging its code training.
  - `replacement`: extracted via regex from the prompt when it is an uppercase word (e.g. `NUMBERS`), otherwise generated.
  - Other strings: a short instruction prompt followed by free completion.

---

## Design Decisions

**Regex for numbers instead of LLM generation.** Numbers in prompts are always explicit and unambiguous. Generating them token by token is slower and error-prone — a simple `re.findall` is faster and correct.

**Greedy decoding for strings.** Sampling or beam search would require more complex stopping logic and offer no benefit for extracting a single short string. Greedy decoding is deterministic and fast.

**Prompt format shapes string quality.** The `regex` parameter uses a code-completion format (`# comment\npattern = "`) which consistently produces better regex syntax than an instruction format, because the model has seen this pattern in training data.

**Post-processing for common model errors.** Three lightweight fixups handle systematic model failures without changing the generation strategy:
- Repeated character collapse: `"****"` → `"*"`.
- Unclosed parenthesis removal: `"([0-9]+"` → `"[0-9]+"`.
- Word boundary injection: bare alphanumeric patterns like `cat` become `\bcat\b`.

---

## Performance

**Function selection: 100% structurally valid, always.** Constrained decoding makes it impossible to emit an invalid function name — the output is guaranteed by construction, not by prompt quality. The number of model forward passes is bounded by the length of the longest function name in tokens.

**Numeric argument extraction: deterministic and instant.** Numbers are read directly from the prompt via regex, with zero model calls. This is both faster and more reliable than generating digits token by token.

**String argument extraction: greedy, up to 80 tokens.** Generation stops as soon as the model emits a closing `"`. In practice this terminates well before the limit. Accuracy depends on prompt clarity and model quality — short, unambiguous strings (names, simple patterns) are extracted reliably; long or complex strings may vary.

**Speed.** The bottleneck is model inference. Each prompt requires one forward pass per token of the function name, plus one per token of each string argument. Numeric parameters cost nothing. All test prompts complete within the 5-minute budget on standard hardware with Qwen3-0.6B.

## Challenges

**Tokenizer as a namespace package.** `llm_sdk` resolves as a Python namespace package during `uv run` without the custom `UV_PROJECT_ENVIRONMENT`, causing `ImportError`. Solved by always running through the Makefile which sets the environment correctly.

**String generation without a stopping signal.** Early attempts masked the `"` token to prevent premature stopping, which caused the model to generate garbage for all 80 steps. The fix was the opposite: stop immediately when the model emits any token containing `"`, treating it as a natural end-of-string signal.

**Replacement strings in uppercase.** For prompts like *"replace numbers with NUMBERS"*, the model generated the replacement character by character instead of the full word. Solved by extracting uppercase words directly from the prompt with `re.search(r'\bwith\s+([A-Z][A-Z]+)\b', ...)`.

**Word boundaries in regex generation.** The model generates `cat` instead of `\bcat\b` for word-match patterns. Solved with post-processing: if the generated pattern is purely alphanumeric, wrap it in `\b...\b`.

## Testing Strategy

Tests are split into four files, all runnable without loading the model:

- **`test_schema.py`**: Pydantic validation — required fields, extra fields, type constraints.
- **`test_parser.py`**: File loading — missing files, malformed JSON, schema mismatches.
- **`test_generator.py`**: Pure functions and mock-model tests — `_get_valid_tokens`, `_build_prompt`, `generate_constrained`, `extract_arguments`.
- **`test_output.py`**: End-to-end correctness — compares the generated output file against expected results, including applying each regex to verify it produces the correct substitution.

The model is mocked in unit tests using `unittest.mock.MagicMock`, injected via `sys.modules` before any `src` imports so the real `llm_sdk` is never loaded during testing.

## Bonus Features

### ✓ Multiple LLM model support

Any HuggingFace causal LM can be used by passing `--model`:

```bash
make run ARGS="--model Qwen/Qwen3-1.7B"
make run ARGS="--model Qwen/Qwen3-0.6B"   # default
```

The model name is forwarded directly to `Small_LLM_Model`, so any model the SDK supports works out of the box.

### ✓ Visualization of the generation process

Pass `--verbose` to see token-by-token generation for every prompt:

```bash
make run ARGS=--verbose
```

Example output:

```
[3/11] Greet shrek...
  [function selection]
    prefix: fn_greet
    selected: fn_greet
  [argument extraction]
    name = "shrek"

[9/11] Replace all numbers in "Hello 34 I'm 233 years old" with NUM...
  [function selection]
    prefix: fn_substitute_string_with_regex
    selected: fn_substitute_string_with_regex
  [argument extraction]
    source_string = "Hello 34 I'm 233 years old"
    regex = "[0-9]+"
    replacement = "NUMBERS"  (from prompt)
```

This makes the constrained decoding process directly observable — at each step, only tokens that extend the prefix toward a valid function name are candidates.

### ✓ Comprehensive test suite

52 unit tests across 4 files, all running in under 0.1 seconds without loading the model:

```bash
make test
```

| File | What it tests |
|---|---|

| `test_parser.py` | File loading — missing files, malformed JSON, schema mismatches |
| `test_generator.py` | Pure functions + mock-model — `_get_valid_tokens`, `_build_prompt`, `generate_constrained`, `extract_arguments` |
| `test_output.py` | End-to-end correctness — verifies each regex actually produces the correct substitution |

The real model is never loaded during tests: `llm_sdk` is injected as a `MagicMock` via `sys.modules` before any import.
